# 设备换号承接关系审计

## 前提与适用范围

任务要求依据维修站交接单与 `sqlite-history` 触发器记录核实承接关系。当前沙箱内
只投放了 `sqlite-history` 库源码，题目所述的真实数据库与交接单原件不在任何可读
位置（上层 `prompt.txt`、`attempt-1` 被沙箱明确封禁，全盘检索无相关库表）。

因此本目录用库自身的触发器机制构建了一个覆盖全部三种数据库操作、且包含"两张
交接单抢认同一后继"情形的等价场景（`repairs.db`），并实现了与具体数据解耦的
核实器。真实数据库到位后，只要表结构为「业务号主键 + 触发器历史表」，直接对
真实库运行 `verify.analyze(库路径)` 即可复用同一套裁定逻辑，无需改代码。

复现：

```bash
.venv/bin/python audit/build_case.py   # 重建 audit/repairs.db
.venv/bin/python audit/verify.py       # 输出完整履历与裁定，见 audit/report.txt
.venv/bin/python -m pytest -q          # 11 个测试锁定裁定行为
```

## 触发器机制（依据 sqlite_history/sql.py 源码）

- INSERT 触发器把 `_version` 硬编码为 1，`_mask` 为全位列掩码（本例 3 列即 7）。
- UPDATE 触发器只写入发生变化的列，未变化列在历史行里是 NULL；`_mask` 按位标记
  变更列（biz_no=1、model=2、status=4），未变化列的 NULL 与"真的被置空"无法区分。
- DELETE 触发器写 `_mask=-1` 并留存删除前全量值，`_version` 取该 rowid 历史
  最大版本 +1。
- `_updated` 是毫秒时间戳，同一事务内多条记录可能同毫秒；核实器按
  `_updated, 历史表rowid` 排序，用历史表自增 rowid 兜底，不能只信时间戳。
- rowid 被删除并复用后，新生命周期的第一条 INSERT 又是 `_version=1`，与旧段
  版本号重复。核实器不按版本号跨段排序，而是在每个物理 rowid 内按
  `DELETE(mask=-1)` / 新 `INSERT(mask=全位)` 切分生命周期段。

## 三种操作的取证含义

1. 改主键（`UPDATE ... SET biz_no=新号`）：物理 rowid 不变、无 DELETE，历史链
   连续，`_mask=1` 直接显示主键改写。这是唯一能被触发器客观证实的承接形式。
2. 删除后复用 rowid：旧设备以 `mask=-1` 终结，新设备以 `mask=1/全位` 的新 INSERT
   开始，版本号从 1 重新计数。触发器只能证明"同一 rowid 槽位先删后建"，不能证明
   两台是同一台物理设备；承接关系只剩交接单单方主张，留作未定。
3. 两件设备交换业务号：每个业务号会同时出现在两个物理 rowid 上，单看业务号无法
   定位设备。必须跟随物理 rowid，并用非键属性（本例 model/status）佐证——属性随
   物理行走，不随业务号走。交换过程还会留下仅存于中间版本的临时号（如 TMP9）。

## 裁定规则

- 确认：前驱与后继出现在同一物理 rowid 的同一生命周期段内，且前驱最后版本早于
  后继最早版本，中间没有 DELETE。
- 未定（证据不足，不强行串链）：
  - 仅在 rowid 复用的不同生命周期段之间出现，链已断裂；
  - 前驱与后继从未共享物理 rowid，尤其前驱物理行仍在册未注销；
  - 同一后继被多张交接单抢认时，所有抢认方一律维持未定，不任选一个串成长链。
- 与争议无关的设备不受影响：仍按物理 rowid 输出独立完整履历，可继续追查。

## 本场景结论（audit/report.txt）

| 交接单 | 声称关系 | 裁定 | 关键依据 |
| --- | --- | --- | --- |
| F1 | A001 → A002 | 确认 | rowid 1 同生命周期，v1→v2 主键改写、无 DELETE |
| F2 | E001 → E002 | 未定 | rowid 5 两段生命周期，先 DELETE 后 INSERT，rowid 复用 |
| F3 | C001 → C002 | 未定 | 无共享 rowid；C001 物理行仍在册；与 F4 抢认 C002 |
| F4 | D001 → C002 | 未定 | 无共享 rowid；D001 物理行仍在册；与 F3 抢认 C002 |

- B001（rowid 2）全程未动，单版本在册，独立可追查。
- TMP9 只是 C001↔D001 交换时的临时号，仅存在于 rowid 3 的中间 UPDATE 版本，
  不是在册设备。
- 交换物证：rowid 3 现挂业务号 D001 但型号仍是"叉车"（原 C001 物理行），
  rowid 4 现挂 C001 但型号是"铲车"（原 D001 物理行），证明业务号与物理设备已脱钩。

## 证据缺口清单

- rowid 复用场景缺少跨生命周期的设备指纹（如机身序列号），无法客观确认
  E001 与 E002 同体；需补维修站实物核验记录或资产序列号台账。
- 交接单本身未纳入触发器跟踪（`handover_forms` 无历史表），单据的事后篡改
  无法从数据库侧发现；如需审计单据，应对其同样 `configure_history`。
- UPDATE 历史行未变化列为 NULL，与"显式置空"不可区分；涉及空值争议时需结合
  上一版本全量快照判断。
- F3/F4 抢认 C002 缺少时间先后之外的排他性证据（签收凭证、双方确认记录），
  在补证前两个连接都必须挂起，C002 自身履历（rowid 6）仍完整可查。
